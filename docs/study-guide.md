# 공부 가이드: 이 코드는 왜 이렇게 짰을까

이 프로젝트를 교재로 삼아, 코드가 **왜** 이런 모양인지 이해하기 위한 가이드입니다.
각 장은 같은 순서로 되어 있습니다.

1. **핵심**: 이 장에서 이해해야 할 한 문장
2. **코드**: 직접 열어 볼 파일
3. **왜 이렇게 했나**: 다른 방법과 비교한 이유
4. **스스로 답해 보기**: 말로 설명해 보는 질문. 막히면 아래 힌트를 펼치세요
5. **실습**: 직접 고치거나 망가뜨려 보는 과제

> 공부 순서 팁: 1장(순수 함수)부터 시작하세요. 테스트가 있어서 혼자 확인하기 가장 쉽습니다.
> 실습은 새 브랜치에서 하고(`git switch -c study`), 끝나면 버리면 됩니다(`git switch main && git branch -D study`).

## 0장. 전체 그림

```
[휴대폰]
  카드 앱 알림 ──▶ PaymentListener(알림 읽기) ──▶ IngestWorker(전송, 재시도)
                                                    │  POST /api/ingest + 기기 토큰
  앱 화면(WebView) ─────────────────────────┐        │
                                           ▼        ▼
[Vercel]                         Next.js 화면     /api/ingest (route.ts)
                                           │        │
                                           │ 로그인  │ 기기 토큰
                                           ▼ 쿠키    ▼
[Supabase]                     Auth + Postgres(RLS)   ingest_context / ingest_save (SQL 함수)
```

이 앱에는 **신원을 확인하는 길이 두 개** 있습니다.

| 길 | 누가 쓰나 | 무엇으로 확인하나 |
|---|---|---|
| 로그인 | 사람이 화면을 볼 때 | 이메일·비밀번호 → 세션 쿠키 → RLS |
| 기기 토큰 | 폰이 알림을 보낼 때 | 마이 탭에서 만든 토큰 → SQL 함수 안에서 해시 비교 |

알림 전송은 사람이 로그인 화면을 거치지 않으니, 따로 기기 토큰이 필요한 겁니다. 이 구분이 이해되면 나머지가 훨씬 쉬워집니다.

**스스로 답해 보기**
- 폰 앱 화면은 왜 직접 그리지 않고 웹사이트를 띄우나요?
- 알림 전송에 로그인 쿠키를 그대로 쓰면 어떤 문제가 있을까요?

<details><summary>힌트</summary>

- 화면을 웹으로 두면 Vercel 배포만으로 폰 화면도 바뀝니다. 앱 재설치가 필요 없고 화면 코드를 한 벌만 관리합니다. 대신 오프라인이나 네이티브 느낌은 약해집니다.
- 알림은 앱이 꺼져 있을 때 백그라운드에서 보냅니다. WebView의 쿠키는 그 시점에 꺼내 쓰기 어렵고, 세션이 갱신되면서 서로 꼬일 수 있습니다. 용도가 좁은 별도 토큰이 더 안전하고 단순합니다.
</details>

## 1장. 순수 함수와 테스트

**핵심**: 계산은 화면과 DB에서 떼어 낸 순수 함수로 두면, 테스트하기 쉽고 어디서든 재사용할 수 있다.

**코드**
- [lib/engine/compute.ts](../lib/engine/compute.ts): 한 달 실적과 혜택 계산 (`computeMonth`)
- [lib/parse.ts](../lib/parse.ts): 알림 문구 해석 (`parsePaymentText`)
- [lib/ingest.ts](../lib/ingest.ts): 알림 하나로 무엇을 할지 결정 (`decideIngest`)
- 각 파일 옆의 `*.test.ts`

**왜 이렇게 했나**
- `computeMonth`는 결제 목록과 시작값만 받아서 결과를 돌려줍니다. DB도 화면도 모릅니다. 그래서 테스트에서는 가짜 결제 몇 건만 만들면 되고, 같은 함수를 달력, 카드 탭, 추천에서 모두 씁니다.
- `decideIngest`는 "판단"만 하고 "저장"은 하지 않습니다. 저장은 SQL 함수가 합니다. 판단과 실행을 나누면 판단 로직을 DB 없이 테스트할 수 있습니다.
- 순수 함수란 같은 입력이면 항상 같은 출력이 나오고, 바깥 상태를 바꾸지 않는 함수입니다.

**스스로 답해 보기**
1. `decideIngest`가 DB에 직접 저장까지 했다면 테스트를 어떻게 써야 했을까요?
2. `computeMonth`는 왜 지난달을 자기 자신으로 다시 호출하나요? (`depth` 인자는 왜 있나요?)
3. `parsePaymentText`는 모르는 부분을 왜 비워 두고, 추측해서 채우지 않나요?

<details><summary>힌트</summary>

1. 테스트마다 DB를 준비하고 비워야 합니다. 느리고, 네트워크와 데이터 상태에 따라 결과가 흔들립니다.
2. 이번 달 혜택을 받을 수 있는지는 지난달 실적으로 정해지고, 지난달 실적은 또 그 전달 혜택에 영향을 받습니다(할인받은 결제가 실적에서 빠지는 카드). 그래서 기록이 있는 달까지 거슬러 올라갑니다. `depth`는 잘못된 데이터로 끝없이 내려가는 것을 막는 안전장치입니다.
3. 틀린 값을 채우면 사용자가 알아채기 어렵습니다. 비워 두면 화면에서 직접 고르게 하거나 보관함으로 보낼 수 있습니다. "모르면 모른다고 하기"는 이 프로젝트 곳곳에 있는 원칙입니다.
</details>

**실습**
1. `npm test`를 돌려 보세요. 무엇이 몇 개 통과하는지 확인합니다.
2. `parsePaymentText`의 몸통을 지우고 직접 다시 써 보세요. `npx vitest run lib/parse.test.ts`가 통과하면 성공입니다.
3. 새 알림 형식을 하나 정해서(예: 다른 카드사 문자) **테스트를 먼저** 쓰고, 그다음 코드를 고쳐 통과시켜 보세요. 이것이 TDD입니다.

## 2장. 시간과 날짜

**핵심**: 시각은 UTC로 저장하고, "며칠인지"는 보여 줄 나라의 시간대로 계산한다.

**코드**
- [lib/engine/month.ts](../lib/engine/month.ts): `monthKey`, `dayKey`, `addDays`
- [lib/engine/compute.test.ts](../lib/engine/compute.test.ts)의 `usesSeoulMonthBoundary`, `dayKey uses Seoul time`

**왜 이렇게 했나**
- DB의 `paid_at`은 시간대가 붙은 시각(`timestamptz`)입니다. 같은 순간을 서울에서는 12월 1일 00:30, UTC로는 11월 30일 15:30이라고 부릅니다.
- 카드 실적은 한국 시간 기준 달로 끊기니, 달과 날짜를 정할 때만 `Asia/Seoul`로 바꿉니다.
- `monthKey`에 캐시가 있는 이유는 결제 수천 건마다 여러 번 불려서입니다. 날짜 변환이 생각보다 비싼 연산이라 측정 후에 넣었습니다.

**스스로 답해 보기**
1. `new Date(iso).toISOString().slice(0, 10)`으로 날짜를 구하면 어떤 결제가 틀린 날짜로 갈까요?
2. `addDays`는 왜 `Date.UTC`로 계산하나요?

<details><summary>힌트</summary>

1. 한국 시간 오전 0시~9시 사이 결제입니다. UTC로는 전날이라 하루 앞 날짜로 갑니다.
2. 날짜만 더하는 계산에 시간대가 끼면 서머타임 같은 데서 하루가 23시간이나 25시간이 되어 어긋날 수 있습니다. 시간대가 없는 UTC로 "달력 계산"만 합니다.
</details>

**실습**
- `dayKey`를 위 1번의 잘못된 방식으로 바꾸고 `npm test`를 돌려 보세요. 어떤 테스트가 깨지는지 확인한 뒤 되돌립니다.

## 3장. 인증과 인가

**핵심**: 인증은 "누구인가", 인가는 "무엇을 해도 되는가"다. 이 앱은 인가를 DB가 직접 지킨다(RLS).

**코드**
- [middleware.ts](../middleware.ts): 로그인 안 했으면 `/login`으로 보냄
- [supabase/migrations/0001_init.sql](../supabase/migrations/0001_init.sql): `enable row level security`, `own rows` 정책
- [app/login/page.tsx](../app/login/page.tsx): `safeNext`

**왜 이렇게 했나**
- 브라우저가 Supabase에 직접 요청하므로, 화면 코드에서 "남의 데이터는 숨기기"를 해 봤자 소용없습니다. 요청을 조작하면 그만이니까요. 그래서 DB가 `user_id = auth.uid()`인 행만 돌려주도록 RLS로 막습니다.
- 미들웨어는 편의 기능(로그인 화면으로 안내)이고, 진짜 보안은 RLS입니다. 둘의 역할을 헷갈리면 안 됩니다.
- `safeNext`는 로그인 후 돌아갈 주소가 우리 사이트 안인지 확인합니다. 확인하지 않으면 남이 만든 링크로 로그인했다가 다른 사이트로 보내지는 공격(open redirect)에 쓰일 수 있습니다.
- 로그인 세션은 쿠키에 저장되고, 미들웨어가 요청마다 갱신합니다. 쿠키 수명은 400일이라 자주 끊기지 않습니다.

**스스로 답해 보기**
1. RLS를 끄면 다른 사용자가 내 결제를 볼 수 있을까요? 어떻게요?
2. 미들웨어만 있고 RLS가 없다면 무엇이 뚫리나요?
3. `safeNext`에서 `//`로 시작하는 주소는 왜 막나요?

<details><summary>힌트</summary>

1. publishable key는 공개된 값이라 누구나 Supabase에 직접 요청할 수 있습니다. RLS가 없으면 로그인한 아무나 전체 행을 읽습니다.
2. 미들웨어는 페이지 접근만 막습니다. Supabase로 가는 데이터 요청은 미들웨어를 거치지 않습니다.
3. `//evil.com`은 브라우저가 "같은 프로토콜의 다른 사이트"로 해석합니다.
</details>

**실습**
- Supabase 대시보드의 SQL Editor에서 `select * from payments;`를 실행해 보세요. 대시보드는 관리자 권한이라 전체가 보입니다. 앱에서는 왜 내 것만 보이는지 정책과 연결해 설명해 보세요. (정책을 실제로 끄는 실습은 하지 마세요. 실서비스 DB입니다.)

## 4장. 요청 받기: 검증과 상태 코드

**핵심**: 바깥에서 들어오는 값은 믿지 말고, 형식을 먼저 검사한 뒤 일을 시작한다.

**코드**
- [app/api/ingest/route.ts](../app/api/ingest/route.ts): 알림 수신 API
- [lib/ingestRequest.ts](../lib/ingestRequest.ts): 헤더와 본문 검사 (`parseIngestRequest`, `dbErrorStatus`)

**왜 이렇게 했나**
- route는 일부러 얇게 두고, 검사는 순수 함수로 뺐습니다. 네트워크 없이 테스트할 수 있어서입니다(1장과 같은 원리).
- 길이 제한(본문 2,000자, 키 200자)은 큰 요청으로 서버를 괴롭히는 것을 막습니다.
- 상태 코드는 받는 쪽이 다음 행동을 정하는 신호입니다.

| 코드 | 뜻 | 폰 앱의 행동 |
|---|---|---|
| 200 | 처리됨(기록, 중복, 무시 포함) | 끝 |
| 400 | 보낸 쪽 잘못(형식 오류) | 다시 보내도 같으니 포기 |
| 401 | 토큰이 틀림 | 포기(연결이 끊겼을 가능성) |
| 500 | 서버 잘못 | 잠시 뒤 다시 시도 |

- 원래는 SQL의 잘못된 입력도 500으로 돌려줘서, 폰이 영원히 재시도하는 버그가 있었습니다. 그래서 SQL 오류 코드 `22023`(잘못된 입력)을 400으로 바꾸는 `dbErrorStatus`를 넣었습니다.

**스스로 답해 보기**
1. 중복 요청에 왜 에러가 아니라 200을 주나요?
2. 400과 500을 구분하지 않으면 무엇이 문제인가요?

<details><summary>힌트</summary>

1. 중복은 "이미 처리됨"이라 성공과 같습니다. 에러로 주면 폰이 실패로 알고 계속 재시도합니다.
2. 재시도해도 소용없는 요청을 계속 보내게 되거나, 반대로 일시적 오류를 포기하게 됩니다.
</details>

**실습**
- `lib/ingestRequest.test.ts`에 테스트를 하나 더해 보세요. 예: `postedAt`이 문자열이면 400.

## 5장. DB 함수와 권한

**핵심**: 권한을 잠깐 높여야 할 때는, 높인 권한으로 할 수 있는 일을 함수 하나에 가두고 입력을 철저히 검사한다.

**코드**
- [supabase/migrations/0005_ingest.sql](../supabase/migrations/0005_ingest.sql): `device_tokens`, `ingest_context`
- [supabase/migrations/0006_ingest_events.sql](../supabase/migrations/0006_ingest_events.sql): `ingest_save`
- [lib/data/deviceTokens.ts](../lib/data/deviceTokens.ts): 토큰 만들기

**왜 이렇게 했나**
- 알림 수신 요청에는 로그인 세션이 없어서 RLS의 `auth.uid()`가 비어 있습니다. 그래서 함수를 `security definer`(함수를 만든 관리자 권한으로 실행)로 만들고, 함수 안에서 **토큰 → 사용자**를 직접 찾습니다. 모든 읽기·쓰기는 그 사용자로만 제한합니다.
- Vercel에 관리자 키(service_role)를 두지 않으려고 이 방식을 골랐습니다. 관리자 키가 새면 전체 DB가 뚫리지만, 이 함수는 할 수 있는 일이 정해져 있습니다.
- `set search_path`를 고정하는 이유는, 누군가 같은 이름의 가짜 함수나 테이블을 다른 스키마에 만들어 관리자 권한 함수가 그걸 부르게 하는 공격을 막기 위해서입니다.
- 토큰은 DB에 sha256 해시로만 저장합니다. DB가 유출돼도 원래 토큰을 알 수 없습니다. 비밀번호를 해시로 저장하는 것과 같은 이유입니다.
- 토큰은 32바이트 무작위 값이라 추측이 사실상 불가능합니다. 그래서 요청 횟수 제한이 없어도 버틸 수 있습니다.

**스스로 답해 보기**
1. `security definer` 함수에서 `user_id`를 요청 본문에서 받으면 어떻게 될까요?
2. 토큰을 해시 대신 암호화해서 저장하면 무엇이 다른가요?
3. `revoke all ... from public` 다음에 `grant execute ... to anon`을 하는 이유는?

<details><summary>힌트</summary>

1. 아무나 남의 `user_id`를 넣어서 남의 계정에 결제를 써 넣을 수 있습니다. 사용자는 반드시 서버가 검증한 값(토큰)에서 나와야 합니다.
2. 암호화는 키가 있으면 되돌릴 수 있습니다. 해시는 되돌릴 수 없고, 비교만 하면 되니 되돌릴 필요도 없습니다.
3. 기본으로 열려 있는 권한을 모두 닫고, 꼭 필요한 대상에게만 다시 엽니다. 최소 권한 원칙입니다.
</details>

## 6장. 멱등성과 동시성

**핵심**: 같은 요청이 여러 번 와도 결과가 한 번 처리한 것과 같아야 한다(멱등성). 네트워크는 언제든 응답을 잃어버린다.

**코드**
- [0006_ingest_events.sql](../supabase/migrations/0006_ingest_events.sql)의 `insert ... on conflict do nothing` 부분
- [android/.../NoticeFilter.kt](../android/app/src/main/java/app/cardperf/NoticeFilter.kt)의 `keyOf`
- [android/.../PaymentListener.kt](../android/app/src/main/java/app/cardperf/PaymentListener.kt)

**왜 이렇게 했나**
- 상황: 서버는 저장했는데 응답이 폰에 도착하기 전에 연결이 끊기면, 폰은 실패로 알고 다시 보냅니다. 키가 없으면 결제가 두 번 생깁니다.
- 그래서 폰이 알림마다 **고정된 키**를 한 번 만들고, 재시도에도 같은 키를 보냅니다. 서버는 처리한 키를 `ingest_events`에 영구히 기록합니다.
- 서버는 "먼저 키를 넣고(insert-first), 넣는 데 실패하면 중복"으로 판단합니다. "먼저 조회하고 없으면 넣기"는 두 요청이 동시에 오면 둘 다 "없음"을 보고 둘 다 넣을 수 있습니다. 기본 키 제약과 `on conflict`는 DB가 이걸 원자적으로 처리하게 합니다.
- 함수 전체가 하나의 트랜잭션이라, 중간에 오류가 나면 넣었던 키도 같이 취소됩니다. 그래서 실패한 요청은 다시 시도할 수 있습니다.

**이 프로젝트에서 실제로 겪은 버그**

| 버그 | 원인 | 고친 방법 |
|---|---|---|
| 응답을 못 받은 재시도가 10분 뒤 또 기록됨 | 중복 판단을 10분 창으로만 함 | 키를 영구 기록 |
| 같은 취소 알림이 다시 오면 다른 결제까지 취소 | 취소 성공 시 키를 안 남김 | 취소도 키 기록 |
| 같은 금액·같은 가게 결제 두 건이 하나로 합쳐짐 | 키를 `앱 + 본문`으로만 만듦 | 키에 알림 시각을 넣음 |
| 삼성이 알림을 다시 올리면 또 기록됨 | 키에 다시 올릴 때 바뀌는 `postTime`을 씀 | 바뀌지 않는 `when`을 씀 |

이 표는 면접에서 "가장 어려웠던 버그"로 그대로 이야기할 수 있습니다.

**스스로 답해 보기**

2. "조회 후 삽입"이 동시 요청에서 왜 깨지는지 시간 순서로 그려 보세요.

## 7장. 안전한 기본값과 재시도

**핵심**: 확실하지 않으면 자동으로 하지 말고 사람에게 넘긴다. 재시도는 하되 끝이 있어야 한다.

**코드**
- [lib/ingest.ts](../lib/ingest.ts): 취소 후보가 정확히 1건일 때만 취소
- [lib/parse.ts](../lib/parse.ts): `findCancelCandidates`
- [android/.../IngestWorker.kt](../android/app/src/main/java/app/cardperf/IngestWorker.kt): 재시도 정책
- [app/review/page.tsx](../app/review/page.tsx): 사람이 확인하는 보관함

**왜 이렇게 했나**
- 같은 카페에서 같은 금액을 두 번 쓴 날 취소 알림이 오면, 어느 쪽 취소인지 알 수 없습니다. 틀린 쪽을 취소하는 것보다 보관함에 넣고 묻는 게 낫습니다. 잘못된 자동 처리는 사용자가 알아채기 어렵고, 되돌리기도 어렵습니다.
- 카드를 모르는 알림, 가맹점을 못 읽은 알림도 버리지 않고 보관함으로 갑니다. 데이터를 잃지 않는 것이 우선입니다.
- 재시도는 WorkManager에 맡깁니다. 앱이 꺼져도, 폰이 재부팅돼도, 인터넷이 다시 연결되면 보냅니다. 간격은 점점 늘리고(지수 백오프), 8번이 넘으면 포기합니다. 끝없는 재시도는 배터리와 서버를 낭비합니다.

**스스로 답해 보기**
1. 재시도 간격을 일정하게(예: 매번 5초) 하면 서버 장애 때 무슨 일이 생기나요?
2. 이 앱에서 "자동"과 "사람 확인"을 나누는 기준을 한 문장으로 말해 보세요.

## 8장. 안드로이드 앱

**핵심**: 앱은 얇게, 꼭 네이티브가 필요한 일(알림 읽기, 지문 잠금)만 한다.

**코드**
- [MainActivity.kt](../android/app/src/main/java/app/cardperf/MainActivity.kt): WebView, 화면 여백, 잠금 덮개
- [Bridge.kt](../android/app/src/main/java/app/cardperf/Bridge.kt), [AppUrl.kt](../android/app/src/main/java/app/cardperf/AppUrl.kt): 웹에서 부르는 `window.CardApp`과 출처 검사
- [PaymentListener.kt](../android/app/src/main/java/app/cardperf/PaymentListener.kt), [NoticeFilter.kt](../android/app/src/main/java/app/cardperf/NoticeFilter.kt): 알림 읽기와 거르기
- [AppLock.kt](../android/app/src/main/java/app/cardperf/AppLock.kt): 지문·PIN 잠금

**왜 이렇게 했나**
- **허용 앱 목록**: 알림 접근 권한은 모든 앱의 알림을 읽을 수 있는 강한 권한입니다. 그래서 카드 앱 목록에 있는 알림만 읽고, 나머지는 내용을 저장하거나 보내지 않습니다. "카톡으로 5,000원 결제했어"가 전송되지 않는 이유입니다.
- **브리지 출처 검사**: WebView에 붙인 `CardApp`은 그 화면에 뜬 어떤 페이지든 부를 수 있습니다. 다른 사이트가 열렸을 때 토큰을 바꿔치기하지 못하게, 지금 화면이 우리 사이트일 때만 동작합니다. 브리지 메서드는 백그라운드 스레드에서 불려서 WebView에 직접 물어볼 수 없으니, 화면이 바뀔 때마다 주소를 `@Volatile` 변수에 적어 둡니다.
- **잠금과 생명주기**: 화면이 안 보이게 되면 `onStop`이 불리니 거기서 잠급니다. 그런데 PIN 입력 화면이 뜰 때도 `onStop`이 불려서 "풀자마자 다시 잠김"이 반복될 수 있습니다. 그래서 인증 중에는 잠그지 않는 `authenticating` 표시를 둡니다.
- 화면 끄기는 `onStop`만으로 확실하지 않아서 화면 꺼짐 신호도 따로 받습니다.

**스스로 답해 보기**

2. 앱 잠금이 서버 데이터를 지켜 주나요? 무엇을 지켜 주나요?

## 9장. 화면(React)

**핵심**: 데이터를 불러오는 일과 계산하는 일을 나누고, 화면은 그 결과를 그리기만 한다.

**코드**
- [lib/data/useMonthData.ts](../lib/data/useMonthData.ts): 불러오기와 계산을 묶은 커스텀 훅
- [lib/data/payments.ts](../lib/data/payments.ts): `listPayments`의 1,000건 단위 읽기
- [app/layout.tsx](../app/layout.tsx), [app/globals.css](../app/globals.css): 다크 모드
- [components/ThemePicker.tsx](../components/ThemePicker.tsx)

**왜 이렇게 했나**
- `useMonthData`는 DB에서 결제를 가져오고(`reload`), 계산은 `useMemo`로 합니다. 결제 목록이 바뀔 때만 다시 계산하고, 화면이 다시 그려질 때마다 계산하지 않습니다.
- Supabase는 한 번에 최대 1,000행만 돌려줍니다. 그래서 1,000건씩 나눠 읽습니다. 이걸 몰라서 결제가 1,000건을 넘으면 실적이 조용히 틀려지는 버그가 있었습니다.
- 다크 모드 색은 CSS 변수로 한 곳에서 바꿉니다. 화면 코드에 색을 직접 쓰지 않았기 때문에 변수만 바꿔도 전체가 바뀝니다.
- `<head>`의 작은 스크립트는 화면을 그리기 **전에** 저장된 모드를 적용합니다. React가 뜬 다음에 바꾸면 한순간 흰 화면이 번쩍입니다. 서버가 그린 HTML과 브라우저 상태가 달라서 생기는 경고는 `suppressHydrationWarning`으로 이 태그에서만 끕니다.

**스스로 답해 보기**
1. `useMemo` 없이 계산을 컴포넌트 몸통에 그대로 쓰면 무엇이 느려지나요?
2. 서버 렌더링(SSR)과 하이드레이션이 무엇인지, 다크 모드 깜빡임과 엮어 설명해 보세요.

**실습**
- `app/globals.css`의 다크 팔레트에서 `--color-page` 하나만 바꿔 보고 화면이 어떻게 바뀌는지 확인하세요.

## 10장. 실무 습관

이 프로젝트를 만들면서 실제로 쓴 습관들입니다.

- **테스트 먼저**: 버그를 고칠 때 그 버그를 재현하는 테스트부터 씁니다(예: `eligibility chain` 테스트). 고친 뒤에도 그 테스트가 다시 망가지는 걸 막아 줍니다.
- **리뷰 받기**: 다른 눈(Codex 리뷰, 검토 에이전트)이 찾은 문제 대부분이 "정상 흐름"이 아니라 **재시도, 동시 요청, 애매한 데이터** 같은 경계 상황이었습니다. 코드를 다 쓰면 "이 입력이 두 번 오면?", "비어 있으면?", "동시에 오면?"을 스스로 물어보세요.
- **작은 커밋**: `git log --oneline`을 보면 커밋마다 한 가지 일만 합니다. 문제가 생기면 어느 커밋이 원인인지 찾기 쉽습니다.
- **비밀 관리**: `.env.local`, `local.properties`는 Git에 올리지 않습니다(`.gitignore`). publishable key는 공개돼도 되는 값이고, service_role key는 절대 앱에 넣지 않습니다.
- **배포 순서**: DB 변경(마이그레이션)을 먼저 적용하고 코드를 배포합니다. 반대로 하면 새 코드가 아직 없는 테이블을 찾습니다.
